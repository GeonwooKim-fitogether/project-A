# 자율 병합 등급 — 중요하지 않은 것은 맡기고, 문제가 되면 되돌린다

> 한 줄 요지: **PR 은 항상 Claude 가 열고, 병합은 변경의 등급에 따라 가른다.** 하(문서·설정·테스트)는 검사가 통과하면 바로 병합하고, 중(일반 기능·버그 수정)은 CC-리드가 직접 검토해 병합한 뒤 결과만 보고하며, 상(DB 구조·실환경 쓰기·운영 배포·인증·권한·시크릿·돈)만 Draft PR 로 두고 건우님이 결정한다. 병합한 것이 문제를 일으키면 되돌림 PR 을 열어 바로 병합하고 보고한다.

건우님이 2026-11-27 에 정한 방침이다 — 중요하지 않은 PR 까지 사람이 확인하면 그것이 병목이므로, **크리티컬이 아니면 자율로 맡기고 문제가 되면 원복한다.** [에스컬레이션 규칙](./escalation.md) 2절의 트리거 6(main 머지)은 하·중에 대해서는 이 규칙으로 대체되고, 나머지 트리거(보안·라이브 DB·비용 등)는 그대로 살아 있다. 언제 멈추고 건우님을 부르는지는 [에스컬레이션 기준](./escalation-criteria.md)에 모은다. 이 규칙은 `branch-guard.py`(브랜치·PR 이름)와 `sql-write-guard.py`(DB 쓰기)를 덮지 않는다 — 두 훅은 등급과 상관없이 그대로 작동한다.

## 1. 등급 — 변경된 경로와 낱말로 가른다

| 등급 | 라벨 | 해당하는 변경 | 병합 |
|---|---|---|---|
| 하 | `tier:low` | 문서(`docs/`, `README.md`, `*.md`), `chore`, 제품 밖 설정, 시험 코드만 | **검사가 통과하면 CC-리드가 바로 병합** |
| 중 | `tier:mid` | 일반 기능, 버그 수정, 리팩터링처럼 하도 상도 아닌 모든 것 | **CC-리드가 diff 를 직접 검토해 병합**하고 결과를 보고 |
| 상 | `tier:critical` | 아래 상 목록의 하나라도 닿는 것 | **Draft PR 로만 두고 병합하지 않는다.** 건우님에게 올린다 |

**상 목록 — 하나라도 닿으면 상이다.**

- 데이터베이스 구조·마이그레이션: `supabase/`, `migrations/`, `*.sql`, `db/` 와 `alter table`·`create table`·`drop`·`rls`·`policy` 낱말
- 실환경 데이터 쓰기, 운영 배포: `production`, `운영`, `deploy`, `배포`, `release` 낱말, `.github/workflows/` 의 신설·변경(Actions 비용·배포 경로가 걸린다)
- 인증·권한: `auth`, `login`, `role`, `permission`, `grant`, `권한`, `인증` 낱말
- 시크릿: `.env*`, `secret`, `token`, `key`, `password`, `credential` 낱말
- 돈: `payment`, `billing`, `price`, `결제`, `청구`, `정산` 낱말
- 안전장치 자체: `.claude/settings.json` 의 permissions, `.claude/hooks/`, 이 규칙 파일. **에이전트가 자기 권한이나 가드를 스스로 넓히지 못하게** 한다. (이 규칙을 처음 넣은 PR 은 건우님이 직접 결정한 하 등급 예외다.)

**판정 방법.** `gh pr diff <번호> --name-only` 로 바뀐 경로를 뽑고, diff 본문에서 위 낱말을 찾는다. 여러 파일이 섞이면 **가장 높은 등급**을 따른다. **애매하면 한 등급 올린다**(하 → 중, 중 → 상). 작업 중 범위가 커져 등급이 올라가면 라벨을 바꾸고 그 등급의 절차로 간다.

## 2. PR 마다 등급 라벨을 붙인다

- 저장소에 `tier:low`(초록) · `tier:mid`(노랑) · `tier:critical`(빨강) 세 라벨이 있다. **모든 PR 에 하나만** 붙인다: `gh pr create --draft --label tier:mid …`.
- PR 은 [브랜치·PR 규칙](./branch-pr-naming.md)대로 Draft 로 열고 작업이 끝나면 `gh pr ready` 로 바꾼다. 상은 Ready 로 바꾸지 않는다.
- 병합은 이력의 커밋 단위 되돌림이 가능하도록 `gh pr merge <번호> --merge` 로 한다(squash 하지 않는다). 브랜치는 워크플로가 지우므로 `--delete-branch` 를 쓰지 않는다.

## 3. 병합 직전 — 상태를 먼저 본다

[상태 먼저](./state-before-action.md)대로 `gh pr view <번호> --json state,isDraft,mergeable,labels,statusCheckRollup` 를 먼저 읽는다.

1. `mergeable` 이 충돌이면 검사는 돌지 않은 것이다. 병합하지 않고 최신 main 을 받아 충돌부터 푼다. `null` 이면 계산이 끝날 때까지 다시 본다.
2. `gh pr checks <번호>` 에 실패가 있으면 병합하지 않고 원인부터 고친다. 검사가 아예 붙지 않았고 충돌도 없으면 바로 병합해도 된다.
3. 라벨이 `tier:critical` 이거나 라벨이 없으면 병합하지 않는다.
4. 중은 diff 를 끝까지 읽고, 본문의 "어디서·무엇을 하면·무엇이 보이나"가 채워졌는지 보고 병합한다.

## 4. 보고 — 이슈 댓글에 세 문장

모든 보고는 **작업 이슈의 댓글 하나, 세 문장**이다. 나쁜 소식도 바로 올린다.

1. **문제** — 무엇이 필요했거나 무엇이 어긋났나.
2. **한 일 또는 제안** — 무엇을 했나(상은 무엇을 하자고 제안하나). PR 링크와 등급을 함께 적는다.
3. **다음 단계와 필요한 허락** — 다음에 무엇을 하나, 건우님의 허락이 필요하면 무엇인지 한 줄. 필요 없으면 "허락은 필요 없다"고 적는다.

```
README 에 작업 등급 안내가 없어 새 작업자가 병합 기준을 찾지 못했다. 한 줄을 추가하는 PR #12(tier:low)를 열고 검사 통과 후 병합했다. 다음 작업으로 넘어가며 필요한 허락은 없다.
```

## 5. 문제가 생기면 — 되돌림 PR 로 바로 원복한다

병합한 하·중 변경이 main 의 검사를 깨거나 동작을 망가뜨렸다는 보고가 오면, **원인을 고치려 들기 전에 먼저 되돌린다.**

1. 상태를 조회한다: `git fetch origin`, `gh pr view <원래 PR> --json mergeCommit,labels`. 원래 PR 이 상이거나 되돌리면 DB·운영 상태와 어긋날 수 있으면 **자동으로 되돌리지 않고** 건우님에게 올린다.
2. 최신 main 에서 새 브랜치를 딴다: `git switch -c fix/revert-<슬러그> origin/main`.
3. 병합 커밋을 되돌린다: `git revert -m 1 <병합 커밋>`. 충돌이 나면 뒤의 변경이 얽힌 것이므로 멈추고 건우님에게 올린다.
4. `git push -u origin fix/revert-<슬러그>` 후 `gh pr create --draft --label <원래 등급 라벨> --title "fix: <원래 PR 요지>를 되돌린다"` 로 열고 본문에 원래 PR 번호·문제·되돌리는 범위를 적은 뒤 `gh pr ready` 로 바꾼다.
5. 3절 절차로 검사 통과를 확인하고 `gh pr merge <번호> --merge` 로 병합한다. 되돌림 PR 자체가 실패하면 멈추고 건우님에게 올린다.
6. 원래 이슈에 4절의 세 문장 보고를 남긴다. 다시 하려면 **새 브랜치·새 PR** 로 한다(머지된 브랜치를 다시 쓰지 않는다).

## 적용 범위

- 이 저장소(project-A)의 모든 세션에 적용된다. 하위 규칙과 부딪히면 더 엄격한 쪽이 이긴다.
- 강제 장치: `.claude/settings.json` 의 허용·확인 목록(git·gh 명령은 허용하되 main 푸시·강제 푸시·브랜치 삭제·저장소 설정은 확인을 거친다). 등급 판정은 글로만 있으므로, **오판을 찾으면 한 줄을 이 규칙에 보태고 건우님에게 올린다.**
