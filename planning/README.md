# 기획 폴더 — 기획 1~8단계 산출물

> 한 줄 요지: **CC-기획이 목적·목표·로드맵·계획·백로그를 이 폴더에 쓰고, 건우님이 PR 로 검토·승인하면 백로그 항목이 `auto` 이슈로 등록되어 자율 루프가 처리함.**

## 1. 흐름 (11-26 확정 흐름도 1~8단계)

- ① 생각 공급: 시드 목적(한 줄) 또는 기존 `purpose.md` 를 입력으로 받음
- ② 목적: `purpose.md` — 왜 하는가, 성공 판단 기준
- ③ 목표: `goals.md` — 측정 가능한 목표 3건 이내
- ④ 로드맵(축): `roadmap.md` — 단계·순서·완료 기준
- ⑤ 계획: `plan.md` — 이번 회차에 착수할 작업 묶음
- ⑥ 디스커션 검토: 기획 PR 에서 건우님이 승인·수정·보류 판단
- ⑦ 백로그: `backlog.md` — PR 하나 크기의 작업 항목
- ⑧ 배분: 승인된 백로그 항목을 GitHub 이슈(`auto` + 등급 라벨)로 등록, 자율 루프가 착수

## 2. 파일 구성

| 파일 | 단계 | 작성 | 비고 |
|---|---|---|---|
| `purpose.md` | 목적 | CC-기획 | 회차가 바뀌어도 유지, 방향 재설정 시에만 변경 |
| `goals.md` | 목표 | CC-기획 | 목표마다 측정 기준 명시 |
| `roadmap.md` | 로드맵 | CC-기획 | 흐름도의 축, 개발 중 발견 문제 반영 |
| `plan.md` | 계획 | CC-기획 | 이번 회차 범위와 순서 |
| `backlog.md` | 백로그 | CC-기획 | 아래 3절 형식 엄수, 이슈 등록 원천 |
| `templates/` | — | 고정 | 각 문서의 빈 양식 |

## 3. 백로그 항목 형식 (자동 등록 대상, 형식 엄수)

```
## B-001 docs: README 에 기획 폴더 안내 절을 더한다
- 등급: tier:low
- 목표: 새 작업자가 README 만 보고 기획 폴더 위치를 파악할 수 있음
- 배경: 기획 폴더 신설 후 README 에 안내 없음
- 완료 조건:
  - [ ] README 에 기획 폴더 절 1개 추가
  - [ ] 링크가 planning/README.md 로 연결됨
- 범위 밖: 기획 문서 내용 변경
- 근거: 계획 P-1 / 목표 G-1
```

- 제목 줄: `## B-<세 자리 번호> <종류>: <한 문장>` — 종류는 feat·fix·docs·chore·refactor·mig 중 하나, 이슈·PR 제목으로 그대로 사용
- 등급: `tier:low` · `tier:mid` · `tier:critical` 중 하나 (판정 기준: `.claude/rules/autonomy-tiers.md`)
- 항목 하나 = PR 하나 크기, 다른 항목 없이 단독 병합 가능해야 함
- 회차당 최대 5건, 위에서부터 착수 순서

## 4. 검토·승인 방법 (6 디스커션 검토)

| 판단 | 방법 | 이후 처리 |
|---|---|---|
| 승인 | 기획 PR 에 `plan-approved` 라벨 부착 또는 PR 병합 | 백로그 항목을 이슈로 등록, 기획 PR 병합 |
| 수정 | PR 에 의견 작성 후 `plan-revise` 라벨 부착 | CC-기획이 의견 반영해 같은 PR 갱신 |
| 보류 | `plan-hold` 라벨 부착 | 이슈 등록·보충 중지 |

- `tier:critical` 항목은 `auto` 라벨 없이 이슈만 등록함 (착수 여부는 건우님 결정)

## 5. 백로그 보충 기준

- 열린 `auto` 이슈(진행 불가 표시 제외)가 **3건 미만**이고 검토 중인 기획 PR 이 없으면 CC-기획이 다음 회차 기획 PR 을 자동으로 올림

## 6. 로드맵 역류 (개발 중 발견한 문제 → 5 로드맵)

흐름도 점선: 결과 모음(10)에서 발견한 문제를 로드맵(5)에 반영함. CC-기획의 다음 회차 입력으로 자동 수집함.

### 입력 두 가지

- ① `needs-attention` 이슈: 자율 루프가 멈춘 과제. 열린 건 전부, 종료된 건 최근 14일 안에 갱신된 것만 모음. 최근 보고 댓글을 함께 넣음
- ② 이슈·PR 댓글 표식: 본문 아무 위치에나 아래 한 줄을 넣음

```
ROADMAP-NOTE: README 제목만 바꾸면 readme-skills 검사가 실패하므로, 검사 스크립트도 함께 고쳐야 함
```

- 표식은 `ROADMAP-NOTE:` (영문 대문자, 콜론, 공백) 뒤에 한두 문장
- 한 댓글에 여러 줄을 써도 되고, 콜론 뒤 그 줄의 문장만 수집함

### 반영 규칙

- 같은 실패 과제를 백로그에 다시 넣지 않음
- `roadmap.md` 변경 이력에 날짜와 함께 적고, 단계 조정이 필요하면 해당 단계의 상태·완료 기준만 고침 (그림 틀은 유지)
- 원인이 반복되면 그 원인을 고치는 항목만 백로그에 추가함
- 수집·반영은 PC 1 의 `Run-Planner.ps1` (`-Mode Propose` 또는 `-Mode Replenish`)이 수행함
## 7. 기존 프로젝트 진입 (흐름도 0)

이미 있는 저장소는 한 줄 씨앗 대신 As-Is 로 읽는다. `Run-Planner.ps1 -Mode Onboard -Repo owner/name` 이 목적·목표·현재 로드맵·열린 백로그 초안과 서비스 등급 제안, 이식 공백을 정리한다. 초안은 이 저장소에 Draft PR 로 올리고, 2. 디스커션에서 건우님이 확인하기 전에는 대상 저장소에 쓰지 않는다. 확인 후 표준 라벨·검사·담당 정의를 대상 관례를 덮어쓰지 않고 PR 로 이식한다. 상세: [docs/existing-project-onboard.md](../docs/existing-project-onboard.md).

## 8. 서비스 등급

프로젝트마다 중요도(사용자·매출·고객사 영향)와 위험도(DB·배포·HW 안전·되돌리기 난이도)로 S·A·B 를 매긴다. 0번에서 제안하고 2번에서 건우님이 확정한다. 확정 값은 `planning/service-grade.md` 에 기록하며, 자동 루프와 기획 반영 가드가 유효 등급 하한으로 읽는다. 파일이 없거나 파싱에 실패하면 B. 이 저장소는 B. 상세: [품질 기준서](../standards/quality.md) ⑨절.

## 9. 프로세스 개선 (흐름도 14)

운영 신호(재시도, `needs-attention`, 가드 차단, 도구 거부, 비용, 사람 개입, `PROCESS-NOTE:`)를 모아 CC-개선이 원인 개선 PR 을 올린다. 문서·프롬프트·스크립트는 검사 통과 시 자율 반영하고, 규칙·설정·훅·틀은 Draft + 결정 카드다. 개선은 Template-repository 에 먼저 넣고 전파한다. 상세: [docs/process-improvement.md](../docs/process-improvement.md).
