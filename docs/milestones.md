# 개발 마일스톤 — 13 건우 검토 진입 규격

> 한 줄 요지: **개발 마일스톤**은 개발 구역에서 건우님의 판단·디렉션이 있어야 다음으로 갈 수 있는 지점이다. 흐름도에서 이 노드는 10 결과 모음 → 11 판단 분기 → 12 보고서 다듬기를 거치지 않고, 점선으로 **13 건우 검토(1:1 채팅)** 에 바로 들어간다.

## 1. 위치

| 항목 | 내용 |
|---|---|
| 흐름도 위치 | 개발 구역의 `개발 마일스톤` 노드 → 13 건우 검토 |
| 연결 | `마일스톤 디렉션 진입 · 📍1:1 채팅` (점선). 13번에서 배분(9번)으로 디렉션이 내려올 수 있음 |
| 담당 | 카드 준비: CC-리드가 개발·검증 산출물을 모음. 전달: GB-A총괄 → GB-보고서 다듬기 → 건우님 1:1 |
| 양식 기준 | 세 문장(문제·해결안·다음 단계) + 결정 한 줄. 틀은 아래 6절 |

일반 결과 보고(10→11→12→13)와 섞지 않는다. 마일스톤이 아니면 이 경로를 쓰지 않는다.

## 2. 마일스톤이란

다음 중 **하나 이상**에 해당하고, 개발·검증만으로 다음 단계를 결정할 수 없을 때 마일스톤으로 본다.

| 번호 | 해당 예 |
|---|---|
| 1 | 제품 단계가 바뀜 — 예: 본체·주변 장치의 시제품 확정, PCB/PCBA 회차 확정, 현장 투입 가능 여부 |
| 2 | 번복 비용이 큼 — 예: 금형·양산 발주, 공구, 대량 PCB 발주, 펌웨어 동결 |
| 3 | 외부 일정·안전·규정에 닿음 — 예: 현장 검증, 인증, 사용자 착용 안전 |
| 4 | 사양 또는 로드맵을 바꿔야 다음 작업이 열림 — 예: 측정 기준 완화, 기능 범위 축소 |

해당하지 않으면 일반 검증 `pass` 뒤 10 결과 모음으로만 보낸다. 애매하면 마일스톤으로 올린다.

## 3. 진입 조건

아래를 모두 갖춰야 13번으로 올린다. 하나라도 빠지면 카드를 만들지 않고 개발·검증을 계속하거나 `blocked`로 표시한다.

- 사양 카드가 있고, 이 지점의 수용 기준이 적혀 있음
- CC-HW검증 또는 CC-SW검증의 최신 검증 카드가 있음 (`pass` 또는 판단에 필요한 `blocked`)
- 확인할 수 없는 항목이 숨겨져 있지 않음
- 6절 양식의 모든 칸이 값으로 채워져 있음(빈칸·자리표시자 없음)

`fail` 상태의 작업 묶음은 마일스톤으로 올리지 않는다. 개발이 수정본을 내고 재검증한 뒤에만 올린다.

## 4. 전달 경로 (1:1)

1. 개발 또는 검증이 작업 묶음·검증 카드에 `마일스톤` 칸을 채운다.
2. CC-리드가 산출물을 모아 6절 카드를 초안으로 쓴다. 읽지 못한 값은 추정하지 않고 "확인 불가"와 사유를 적는다.
3. GB-A총괄이 한눈에 읽히는지 걸러, GB-보고서가 6절 양식(세 문장·표·결정 한 줄)으로 다듬는다. 일반 현황 보고의 흐름도 틀은 이 카드에 끌어오지 않고, 바꾸지도 않는다.
4. **건우님 1:1 채팅**으로만 올린다. 프로젝트 방·다른 주제로 올리지 않는다.
5. 건우님 디렉션은 13번에서 배분(9번)으로 내려가거나, 방향이 어긋나면 2 디스커션·로드맵 조정으로 간다. 세션이 디렉션을 추정해 실행하지 않는다.

## 5. 하지 않는 일

- 마일스톤이 아닌 일반 진행 보고를 이 경로로 올리는 일
- 검증 전·결함 미해결 상태로 올리는 일
- 1:1이 아닌 곳(프로젝트 방, 다른 주제 방)에 올리는 일
- 건우님 이름으로 PR 리뷰·승인 의견을 남기는 일
- 결정 전에 PLM 제출, 발주, 현장 배포를 실행하는 일

## 6. 마일스톤 카드 양식

아래를 그대로 복사해 값만 채운다. 칸 이름과 순서를 바꾸지 않는다. 전달 전에 빈칸이 남아 있지 않아야 한다.

```
**개발 마일스톤 (<YYYY-MM-DD HH:mm> KST)**

- 문제: <지금 막힌 판단, 한 문장>
- 해결안: <개발·검증이 확인한 사실, 한 문장>
- 다음 단계: <디렉션이 나오면 할 일, 한 문장>

| 칸 | 내용 |
|---|---|
| 대상 | 본체 / 주변 장치 / PCB·PCBA / 웹·앱 / 연동 (해당만), 품목·이슈 번호 |
| 이 지점 | 무엇의 어떤 단계인지 (예: 본체 시제품 현장 투입 여부) |
| 확인한 사실 | 검증 카드 판정, 핵심 측정값, 성적서 위치 |
| 확인하지 못한 것 | 없으면 "없음" |
| 선택지 | 2~3개. 각 선택지의 효과와 번복 비용 |
| 권고 | 한 줄. 권고가 없으면 "권고 없음, 판단 요청" |

**결정 요청:** <승인·선택한 뒤에 일어나는 일 한 줄>
```

예시(형식만, 실제 판단에 쓰지 않음):

```
**개발 마일스톤 (2026-11-29 18:00 KST)**

- 문제: 본체 시제품의 현장 투입 여부를 개발·검증만으로 확정할 수 없음
- 해결안: 실내 측정은 수용 기준을 통과했고, 우천 조건은 확인하지 못함
- 다음 단계: 현장 투입 범위(실내만 / 우천 포함 보류)를 정하면 다음 시험 계획을 배분함

| 칸 | 내용 |
|---|---|
| 대상 | 본체, 이슈 번호는 배분 후 기입 |
| 이 지점 | 시제품 현장 투입 여부 |
| 확인한 사실 | HW 검증 1회 pass, 실내 위치 오차 기준 충족, 성적서 경로는 작업 묶음에 있음 |
| 확인하지 못한 것 | 우천·금속 스탠드 환경 |
| 선택지 | 1) 실내 시험만 투입 2) 우천 시험 후 재판단 3) 투입 보류 |
| 권고 | 우천 시험 후 재판단 |

**결정 요청:** 선택지 2를 승인하면 우천 시험을 다음 과제로 배분함
```
