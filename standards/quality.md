# 품질 기준서

> 한 줄 요지: **크리티컬이 아니면 자율로 맡기고, 문제가 되면 원복함.** 하·중 등급은 검사 통과 후 반영, 상 등급은 Draft PR 로만 두고 건우님이 결정함. 같은 검사가 실패하면 1회만 재시도하고, 다시 실패하면 멈춰 `needs-attention` 라벨과 세 문장 댓글로 보고함.

근거: `.claude/rules/autonomy-tiers.md`(자율 병합 등급), 에스컬레이션 기준 초안(구 저장소 PR #13, **미승인 Draft**), `.github/workflows/` 검사. 이 문서는 규칙을 요약한 것이며 원문이 우선함.

## ① 등급과 반영 방식

| 등급 | 라벨 | 해당 | 반영 |
|---|---|---|---|
| 하 | `tier:low` | 문서·README·시험 코드·제품 밖 설정 | 검사 통과 시 CC-리드가 바로 반영 |
| 중 | `tier:mid` | 일반 기능·버그 수정·정리 | CC-리드가 변경 내용을 끝까지 검토 후 반영, 결과만 보고 |
| 상 | `tier:critical` | 상 목록에 하나라도 닿는 변경 | Draft PR 로만 두고 반영하지 않음, 건우님 결정 |

- 상 목록 원문: `.claude/rules/autonomy-tiers.md` 1절 (DB 구조, 실환경 쓰기, 외부 반영, 접근 통제, 비밀 정보, 금전, 안전장치 파일)
- 여러 파일이 섞이면 가장 높은 등급, 애매하면 한 단계 올림
- PR 마다 등급 라벨 하나, 범위가 커지면 라벨을 올려 해당 절차로 전환함
- 반영은 병합 방식(--merge)으로 하며 이력 단위 원복이 가능해야 함
- 프로젝트의 서비스 등급이 S 또는 A 이면, 위 표의 자동 반영 범위가 더 좁아진다. ⑨절

## ② 검사 (PR 마다 자동)

| 검사 | 확인 내용 |
|---|---|
| 브랜치·PR 정책 / 브랜치·PR 검사 | 이름 형식, PR 제목 `<종류>: <한 문장>`, 겹침, 실행 가능 여부 |
| README 스킬 표 검사 | 스킬 목록 표와 실제 스킬의 일치 |
| 파일 등록부 검사 | 미등록 파일 경고 |
| 자산 그래프 정합 검사 · 웹앱 환경 표준 검사 | 해당 경로를 건드릴 때 정합성 |

- 검사 실패 상태에서는 반영하지 않음, 검사가 아예 붙지 않았고 충돌도 없으면 반영 가능
- 충돌이 있으면 검사가 돌지 않은 것이므로 최신 main 을 받아 충돌부터 해결함

## ③ 반영 직전 점검

- [ ] 상태 먼저 조회함 (`state`, `isDraft`, `mergeable`, 라벨, 검사 결과)
- [ ] 라벨이 있고 `tier:critical` 이 아님
- [ ] 검사가 모두 통과함, 충돌 없음
- [ ] 중 등급은 PR 본문 "어디서·무엇을 하면·무엇이 보이나"가 채워져 있음
- [ ] 금지 경로(`.claude/**`, 설정, 훅, 비밀 정보)를 건드리지 않았음 (건드렸다면 상 등급)

## ④ 실패·재시도

| 순서 | 상황 | 행동 |
|---|---|---|
| 1 | 검사 첫 실패 | 원인을 고치고 **1회 재시도** |
| 2 | 같은 검사 재실패 | 세 번째를 돌리지 않고 멈춤, `needs-attention` 라벨 + 세 문장 댓글 |
| 3 | 알려진 실패 | 실행기가 스스로 처리 (재시도·대기) |
| 4 | 모르는 실패 | 멈추고 이유 한 줄과 사람이 할 일을 남김 |

- 가드 훅이 막으면 우회하거나 끄지 않고 멈춰 보고함
- `needs-attention` 시 시험 범위 밖 변경으로 번지지 않게 PR 은 그대로 둠 (닫기·삭제는 건우님 판단)
- 2회 모두 실패하는 경로는 실증 시험 진행 중이며, 결과가 나오면 이 절을 갱신함

## ⑤ 원복

- 반영한 하·중 변경이 검사나 동작을 깨면 원인 수정보다 **먼저 원복 PR** 을 열어 반영하고 즉시 보고함
- 원래 PR 이 상이거나, 충돌·DB·외부 반영 상태와 어긋나면 자동 원복하지 않고 건우님께 올림

## ⑥ 보고 (이슈 댓글 하나, 세 문장)

1. 문제: 무엇이 필요했거나 어긋났는가
2. 한 일 또는 제안: PR 링크와 등급 병기
3. 다음 단계와 필요한 허락: 없으면 "허락은 필요 없다"

- 정상 반영은 이슈 댓글만 남기고 Wayfinder 방은 울리지 않음, 문제가 있을 때만 방에 올림
- 나쁜 소식은 즉시, 형식은 [보고 기준서](./report.md)를 따름

## ⑦ 독립 검증 (설계 중)

- CC-SW검증 담당이 개발 담당과 분리되어 반영 전 별도 확인하는 단계를 설계 중임 (구 저장소 PR #22 Draft)
- 반영·확정 후 이 절에 기준을 옮김

## ⑧ 완료 기준 (PR 하나)

- [ ] 등급 라벨 하나, 제목·브랜치 형식 준수
- [ ] 모든 검사 통과, 충돌 없음
- [ ] 이슈에 세 문장 보고 완료
- [ ] 검증하지 못한 항목을 "검증 완료"로 표시하지 않았고 확인 범위를 명시함
- [ ] 범위 밖 변경 없음
## ⑨ 서비스 등급 (프로젝트 단위 하한)

작업 등급(하·중·상) 위에, 저장소마다 서비스 등급을 둔다. 0. 기존 프로젝트 진입에서 중요도(사용자·매출·고객사 영향)와 위험도(DB·배포·HW 안전·되돌리기 난이도)로 판정하고, 2. 디스커션에서 건우님이 확정한다. 확정 값은 `planning/service-grade.md`에 기록한다. 자동 루프와 기획 반영 가드가 이 파일을 읽어 유효 등급 하한을 올린다. 파일이 없거나 읽지 못하면 **B**(현행 유지).

| 서비스 등급 | 예시 | 자동 병합 | 건우님 최종 점검 |
|---|---|---|---|
| S 운영 핵심 | 운영 중인 사내 핵심 서비스 | 문서만 (`docs/`, `planning/`, `standards/`, 루트 문서, `*.md`) | 코드·배포·DB는 전부. 결정 카드에 **영향 범위·검증 증거·되돌림 방법** 필수 |
| A 운영 보조 | 내부 도구 | 시험과 문서만 (제품 코드 제외) | 기능 변경·배포·DB |
| B 신규·실험 | project-A | 현재 규칙 그대로 (①절) | 설정·권한·비밀정보, 그리고 상 목록에 닿는 변경 |

- A등급의 자동 병합 범위는 시험(tests/fixtures/spec)과 문서뿐이며 제품 코드는 포함하지 않음
- 이 저장소의 현재 값: [planning/service-grade.md](../planning/service-grade.md) (B)
- 등급 변경은 건우님 확정 후에만 그 파일을 고친다
- 하한에 걸려 자동 병합하지 못하면 Draft/대기로 두고 결정 카드를 채운다
